# 9. PWA on Cloudflare's Workers static-assets platform: platform guards, service worker, generated icons

- **Status:** Accepted
- **Date:** 2026-07-23

## Context

Phase 3 (per the original plan) is distribution: ship the same codebase as an installable, offline-capable PWA, hosted on Cloudflare (chosen over Netlify for edge network size and free bandwidth — see the original planning conversation, which specified "Cloudflare Pages"). Dropping SQLite back in Phase 0 was explicitly meant to make this path simple, since `AsyncStorage` falls back to `localStorage` on web with no extra work. What Phase 0 didn't anticipate was every *other* native module added since — notifications, file system, sharing — each needed to be checked against its actual web behavior rather than assumed.

## Decision

### Web compatibility is verified from source, not assumed

Two real incompatibilities were found by reading the installed packages' source, not by guessing:

1. **`expo-notifications` scheduling throws on web.** `NotificationScheduler.ts` — the module Metro resolves for web, since there's no `.web.ts` override — only stubs `addListener`/`removeListeners`; calling `scheduleNotificationAsync` there throws `UnavailabilityError`. Permission APIs (`getPermissionsAsync`/`requestPermissionsAsync`) *do* work on web, via the browser's own `Notification` API — which is exactly why a permission check alone can't guard this. `features/notifications/schedule.ts` exports `supportsScheduledNotifications = Platform.OS !== "web"`; `scheduleForBlock`/`cancelNotifications` no-op on web instead of throwing, and Settings shows "not available on web" instead of a button that would do nothing.

2. **`expo-file-system`'s `File`/`Directory` classes are non-functional on web.** The web module (`ExpoFileSystem.web.ts`) is a stub whose constructors only `console.warn`. Backup export uses a `Blob` + temporary `<a download>` on web instead (the standard browser pattern) and the native `File`/`Paths`/`Sharing` path elsewhere; backup restore reads `expo-document-picker`'s web-native `asset.file.text()` (a real browser `File` object) rather than routing through `expo-file-system`, which can't read a `blob:` URI on web anyway. See `features/backup/io.ts`.

Two further web-only defects surfaced after the first live deploy, each blanking the render, each verified from the running bundle rather than guessed:

3. **`import.meta` is a parse-time `SyntaxError` in the classic-script web bundle.** Zustand's `devtools` middleware reads `import.meta.env.MODE`; even though the app only uses `persist`, the `zustand/middleware` barrel drags `devtools` into the bundle, and Metro serves web output as a classic script (not a module), so the token aborts the whole file before any code runs. A Babel plugin in `babel.config.js` rewrites every `import.meta` to `{}` (the devtools guard then reads `undefined` and no-ops). Native is unaffected.

4. **NativeWind's `colorScheme.set()` throws on web under `darkMode: 'media'`.** `_layout.tsx` applies the user's saved theme with `colorScheme.set(mode)`. Under the Tailwind default (`darkMode: 'media'`, the system controls the scheme via `@media`), that call throws on web — but not on native, which is exactly why it passed in Expo Go and blanked in the browser. `tailwind.config.js` sets `darkMode: "class"` so the scheme is a root class the app can drive.

### Icons are placeholder artwork, generated by script, not hand-authored

No app icon existed anywhere before this pass. Rather than leave the PWA installable with a blank icon, `scripts/generate-icons.js` uses `jimp-compact` (pure JS, already a transitive dependency, no native binary/build tools needed) to composite a simple geometric "T" monogram in terracotta — the original Tonalli brand accent — onto the required native and web icon sizes. This is explicitly a placeholder, not final artwork; `npm run generate-icons` regenerates it, and `app.json`/`public/manifest.json`'s paths won't need to change whenever real artwork replaces these files.

### Offline via a runtime-caching service worker, not a precomputed manifest

Metro's JS/CSS output filenames are content-hashed per build, so a service worker can't ship a static list of "files to precache" without a build step to generate it. `public/sw.js` instead caches whatever it actually sees fetched — after one online visit, the app shell, JS, CSS, and route HTML are all cached and the app loads and functions fully offline. `CACHE_NAME` is versioned by hand; bumping it forces every visitor's cache to reset on the next deploy.

Two request classes get opposite strategies, because they have opposite needs. **Navigations (the HTML shell) are network-first:** the freshest HTML wins whenever the network is reachable, so a new deploy's HTML — which references the new content-hashed asset URLs — is picked up on the next reload with no manual `CACHE_NAME` bump; the cached copy is only the offline fallback. **Immutable hashed assets (JS/CSS/icons) stay cache-first** with a background refresh, since their filenames never change. This replaced an all-cache-first design that stranded visitors on stale HTML after every deploy. The fetch handler also skips non-`http(s)` requests, which otherwise throw on `Cache.put` for browser-extension URLs.

### Two Expo Router static-export quirks, worked around in `+html.tsx`

- **The host needs a literal `404.html`**, but Expo Router's web export names its not-found page `+not-found.html`. `scripts/postexport-web.js` copies one to the other after every export (`npm run build:web` runs both steps). Without it, the deploy assumes the whole site is a single-page app and silently routes every unmatched path to `/` instead of showing a real 404.
- **Every route ships an empty `<title>`.** Expo Router's static export unconditionally injects its own empty `react-helmet-async` title slot at the front of `<head>`, regardless of whether the code uses `expo-router/head`'s `<Head>` — which only fills that slot for a screen react-navigation considers "focused", never true during the static prerender pass. Confirmed by inspecting the generated HTML, not assumed. Fixed with an inline script (`document.title = "TonalliBlock"`, which the DOM spec defines as retargeting the *first* `<title>` in the document — the empty one), run once synchronously in `<head>` and once more on `window.load` as a guard against Helmet's client-side hydration re-emptying it.

### Cloudflare Pages, mid-migration to Workers — discovered during deploy, not planned for

The plan (from the original Phase 0 conversation) said "Cloudflare Pages". By the time this shipped, `wrangler pages deploy` had started auto-delegating to "the latest version of Cloudflare Pages, now part of Cloudflare Workers" and failing outright, because `wrangler.jsonc` had Pages' `pages_build_output_dir` key instead of the new model's `assets` block. Confirmed against current Cloudflare docs (fetched live, not from training data, since this is exactly the kind of recently-changed platform detail worth double-checking) rather than fighting the delegation: `wrangler.jsonc` uses

```jsonc
{
  "name": "tonalliblock",
  "compatibility_date": "2026-07-23",
  "assets": { "directory": "./dist", "not_found_handling": "404-page" }
}
```

`main` (a Worker script entrypoint) is optional and correctly omitted — this is a pure static site, no server code. Deploy command is `wrangler deploy`, not `wrangler pages deploy`. `public/_headers`' cache rules are still honored under this model (verified post-deploy: the JS bundle's response carried `Cache-Control: public, max-age=31536000, immutable` as configured).

Live at **https://tonalliblock.maurixio-torrez.workers.dev**.

## Consequences

- `wrangler.jsonc` + `npm run deploy:web` (`expo export --platform web --clear` → copy 404.html → `wrangler deploy`) is the whole deploy pipeline for a project with no backend and no server-side routes. The `--clear` is load-bearing: a build over a stale Metro cache once emitted an `index.html` referencing a bundle hash that was never written to `dist`, so the deploy shipped HTML pointing at a 404'd bundle and blanked the app. A clean export keeps HTML and its hashed assets consistent.
- `public/` is the convention for anything that needs a stable, unhashed URL — manifest, service worker, PWA icons, `_headers` — confirmed by testing that Expo's web export copies its contents to the output root verbatim.
- Post-deploy verification used `curl` against the live URL (status codes, headers, clean-URL routing, 404 behavior, JS bundle integrity/size) rather than a browser-rendering fetch tool, since this app's static HTML is a shell with no pre-rendered visible content — a non-JS-executing fetch reporting "blank page" here is expected, not a deploy failure signal.
- **Known gap:** a real design pass on the app icon/splash art is still owed. The generated monogram is legible and on-brand color-wise, but is not a substitute for actual icon design.
